## 0. 한 줄 요약

**영화 네비게이터와 같은 저장소·같은 앱에, 조선시대부터 현재까지의 한국사를 다루는
두 번째 GraphRAG 를 탭으로 붙인다.**
위키백과 산문에서 `인물 · 조직 · 사건` 과 그 관계를 뽑아 그래프로 쌓고,
"A가 참여한 사건에 같이 있던 인물이 세운 조직은?" 처럼 **다리를 건너야만 닿는 질문**에
근거와 경로를 함께 붙여 답한다.

**제출물은 저장소 전체다.** 하나의 GraphRAG 엔진에 **🎬 영화 · 🏛 인물** 두 도메인이
탭으로 붙은 형태이고, README 와 REPORT 는 **두 도메인을 함께** 다룬다 (§9).

```
저장소 GojoSuperman/graph-navigator   (movie-navigator 에서 이름 변경 완료)
배포   graph-navigator.vercel.app     (다음 배포부터. 아직 공개 전이다)

 ┌──────────────────────────────────────────┐
 │  🎬 영화   │   🏛 한국사                   │  ← 상단 도메인 탭
 ├──────────────────────────────────────────┤
 │  질문 · 탐색기 · 지도        │   3D (붙박이) │
 └──────────────────────────────────────────┘
```

## 1. 왜 한국사인가

과제는 "이전에 구축해 본 영화 GraphRAG 를 바탕으로 **여러분의 도메인**에 적용" 을 요구한다.
도메인을 고르는 기준을 셋으로 두었다.

| 기준 | 한국사가 맞는 이유 |
|---|---|
| **한 문서만 읽어서는 답이 안 나올 것** | 《안창호》 문서에 《의열단》은 없고, 《의열단》 문서에 《안창호》는 없다. 둘을 잇는 것은 **사건이나 제3의 인물**이다 |
| **개체가 문서 사이에 겹칠 것** | 한 인물이 여러 조직·사건에 걸친다. 신민회 ↔ 105인 사건 ↔ 흥사단이 인물로 엮인다 |
| **답이 맞는지 검증할 수 있을 것** | 위키백과 원문에 관계 서술이 문장으로 있다. 근거 문장을 그대로 들고 오면 사람이 1초에 확인한다 |

**영화와 다른 점이 하나 있고, 그것이 이 과제의 핵심이다.**
영화는 출연·연출 관계가 TMDB 크레딧에 **이미 구조화돼** 있어서 규칙으로 뽑았다.
위키백과는 산문이다. 그래서 이번에는 **LLM 으로 관계를 추출**해야 하고,
과제가 요구하는 `① 추출 → ② 정제·병합` 단계가 비로소 진짜로 드러난다.

> **이것이 가장 큰 위험이기도 하다.** LLM 추출은 없는 관계를 지어낼 수 있다.
> 대응은 §4 에 적는다 — 근거 문장을 반드시 함께 뽑게 하고, 원문에 그 문장이
> 실재하는지 **코드로 검증**해 통과 못 하면 엣지를 버린다.

## 3. 수집 설계

### 범위를 600년으로 넓힐 때 생기는 문제를 먼저 적는다

조선(1392)부터 현재까지는 **600년**이다. 처음 잡았던 독립운동기(약 50년)보다 12배 넓다.
넓히면 좋아지는 것과 나빠지는 것이 분명하게 갈린다.

| | |
|---|---|
| **좋아지는 것** | 질문 폭이 넓다. 세종·정약용·김구·김대중을 한 도구로 물을 수 있다 |
| **나빠지는 것** | **다리가 얇아진다.** 같은 문서 수로 12배 넓은 시대를 덮으면 인물끼리 겹칠 일이 줄어들고, 겹치지 않으면 **멀티홉 질문 자체가 성립하지 않는다** |

이 프로젝트가 증명해야 하는 것이 멀티홉이므로, **얇아지는 쪽이 치명적이다.**
그래서 넓히되 다음 두 가지로 받친다.

1. **문서 수를 70 → 140 건으로 올린다.** (과제 최소는 50건. 넉넉히 넘긴다)
2. **시대별로 촘촘한 덩어리를 만든다.** 시드를 시대마다 묶어서 넣어, 한 시대 안에서는
   인물·조직·사건이 빽빽하게 엮이게 한다. 시대를 **가로지르는** 다리는 자연히 얇을
   텐데, 그것을 감추지 않고 **한계로 같이 보고한다**(§7).

> **이것은 가설이고, 1단계가 끝나면 숫자로 확인한다.** 엣지 밀도(인물당 평균 연결)가
> 기준 미달이면 시대를 좁히거나 문서를 더 넣는다. **재기 전에는 되는 줄 알고 진행하지 않는다.**

#### 재고 나서 — 가설은 절반만 맞았다 (2026-09-21, `scripts/history/density.ts`)

문서 140건의 **언급 그래프**(A 본문에 B 제목이 나오면 연결)로 쟀다. 진짜 엣지는
2단계 뒤에 나오지만, 언급이 없으면 LLM 도 뽑을 수 없으므로 **이것이 엣지 수의 상한**이다.

```
엣지 2,513개 · 평균 차수 27.6 · 연결 요소 1개(고립 0건) · 다리 후보 99건

시대 내부   조선 전·중기 275 · 조선 후기 300 · 구한말·일제 327 · 해방·현대 426
시대 교차   1,185개
```

| 예상 | 실측 |
|---|---|
| "넓히면 다리가 얇아진다" | **아니었다.** 평균 차수 27.6, 고립 0건, 한 덩어리 |
| "시대를 가로지르는 다리는 자연히 얇다" | **아니었다.** 교차 1,185개로 내부 합계(1,328)와 맞먹는다 |
| "조선 쪽이 현대사보다 얇을 것" | 얇긴 하나 **현대사의 70% 수준** — 예상만큼은 아니다 |

**넓힌 대가가 예상만큼 크지 않았다.** 다만 이것은 언급 그래프이고, 언급이 곧 관계는
아니다. 2단계 뒤 **진짜 엣지로 다시 재서** 두 숫자를 나란히 REPORT 에 싣는다.

### 시드 — 네 시대 × 각 7건

```
조선 전·중기   세종 · 이순신 · 정도전 · 집현전 · 훈민정음 · 임진왜란 · 성균관
조선 후기      정약용 · 정조 · 흥선대원군 · 규장각 · 실학 · 동학 농민 혁명 · 갑오개혁
구한말·일제    안창호 · 김구 · 안중근 · 신민회 · 대한민국 임시정부 · 3·1 운동 · 의열단
해방·현대      이승만 · 박정희 · 김대중 · 4·19 혁명 · 5·18 민주화 운동 · 6월 항쟁 · 제헌 국회
```

각 시대마다 **인물·조직·사건 세 타입을 섞는다.** 인물만 시드로 두면 2홉 후보도
인물로 쏠려 조직·사건 노드가 빈약해진다. 스키마가 세 타입이면 시드도 셋이어야 한다.

### 2홉으로 넓히는 이유

1홉(시드가 직접 링크한 문서)만 모으면 시드끼리만 이어진 **별 모양**이 된다.
그러면 "A와 B 사이의 다리" 질문을 만들 수 없다 — 다리가 언제나 시드이기 때문이다.
2홉을 넣어야 **시드가 아닌 인물이 두 시드를 잇는** 구조가 생긴다.

### 채택·탈락 기준 (과제가 명시적으로 요구)

| 단계 | 기준 | 왜 |
|---|---|---|
| 후보 순위 | **여러 시드가 함께 가리킨 문서** 우선 | 둘을 잇는다는 것이 곧 다리라는 뜻 |
| 시대 배분 | 시대별 **할당량**을 두고 채운다 | 문서가 많은 현대사로 쏠리는 것을 막는다. 안 두면 조선 전기가 비어 버린다 |
| 분류 필터 | 시드와 **분류 1개 이상 공유** | 링크가 있다고 같은 주제가 아니다 (안창호 문서는 '미국'도 링크한다) |
| 제외 | `연도 · 연도대 · 목록 · 틀: · 분류: · 일람` | **1919년 문서는 링크가 수천 개라 모든 인물을 서로 잇는 허브가 된다.** 다리가 아니라 지름길이 생긴다 |
| 토막글 | 본문 **800자 미만 탈락** | 관계 서술이 없어 엣지를 못 만든다 |
| 목표 | **140건** (시대당 35건) | 과제 최소 50건 + 600년을 덮을 밀도 |

### 호출 설계 — 이미 한 번 깨졌다

`prop=extracts` 는 한 번에 한 문서만 받는다. 반면 분류는 20건씩 묶어 받는다.
그래서 **분류로 먼저 거르고 살아남은 것의 본문만** 한 건씩 받는다. 호출이 수백 번 줄어든다.

> **첫 실행에서 `429 Too Many Requests` 로 멈췄다** (시드 4번째 이회영).
> 0.3초 간격으로는 부족했다. 대응: 지수 백오프 재시도 + `Retry-After` 존중 +
> 간격 상향. **측정해서 고친다** — 몇 초가 필요한지는 돌려 봐야 안다.
> 시드가 28건으로 늘었으므로 이 대응 없이는 반드시 다시 막힌다.

## 4. 온톨로지 (스키마)

### 노드 3종

| 타입 | 무엇 | 예 |
|---|---|---|
| `Person` | 사람 | 세종 · 정약용 · 안창호 · 김대중 |
| `Organization` | 단체·정부·학교·신문 | 집현전 · 규장각 · 신민회 · 임시정부 |
| `Event` | 사건·운동·전투·개혁 | 임진왜란 · 갑오개혁 · 3·1 운동 · 5·18 민주화 운동 |

### 시대(Era)는 노드가 아니라 **속성**으로 둔다

600년을 다루니 "조선 후기" 같은 시대 구분이 필요해 보인다. 그런데 **노드로 만들면 안 된다.**

```
시대를 노드로 두면:
   정약용 ──▶ [조선 후기] ◀── 정조 ◀── … 그 시대 인물 전부
   → 같은 시대에 살았다는 이유만으로 모두가 2홉 이웃이 된다
```

이것은 다리가 아니라 **지름길**이다. "정약용과 같은 시대 인물" 은 멀티홉 추론이 아니다.
그래서 시대는 각 노드의 **속성**으로만 두고, 탐색에는 쓰지 않는다. **화면의 필터와
평가의 묶음 구분**에만 쓴다. (연도 문서를 코퍼스에서 제외하는 §3 과 같은 이유다.)

### 스키마가 근대 정치사에 치우쳤다 — 8단계에서 드러난 한계

화면을 만들다 발견했다. 문서는 시대마다 35건으로 같은데 **관계는 4배 넘게 벌어진다.**

```
구한말·일제  670   소속 218 · 이끔 192 · 설립 120     ← 조직 중심
해방·현대    435   이끔 156 · 소속 143 · 참여 71
조선 후기    206   참여 56 · 사사 48 · 이끔 38        ← 조직 관계가 얇다
조선 전·중기  154   참여 50 · 사사 47 · 이끔 29
```

위키백과 서술 밀도 차이도 있지만 **더 큰 원인은 스키마다.** 관계 6종 중
`FOUNDED · MEMBER_OF · LED` **셋이 조직을 전제**한다. 근대에는 신민회·임시정부·
정당이 있지만 **조선에는 근대적 조직이 드물다.**

조선 인물의 주된 관계는 **관직 · 혼맥 · 사화 · 붕당**인데 —

| | |
|---|---|
| **관직** | §5 에서 **일부러 뺐다** (《전라도관찰사》는 자리이지 조직이 아니다). 맞는 판단이었지만 **그 결과 조선 인물의 주 관계가 통째로 빠졌다** |
| **혼맥 · 사화** | 애초에 스키마에 없다 |

**스키마를 근대 정치사에 맞춰 짜놓고 600년에 적용한 셈이다.** §1 이 "한 도구로
세종·정약용·김구·김대중을 물을 수 있다" 를 넓히는 이점으로 들었는데, 그 이점은
**관계 타입이 시대를 타지 않을 때만** 성립한다.

> **고치지 않고 적는다.** `HELD_OFFICE`(Person → 관직) 같은 관계를 넣으면 조선이
> 두꺼워지겠지만, 2단계 재추출 · 3단계 재정제 · 5~7단계 재평가가 전부 따라온다.
> 평가와 동결이 끝난 뒤에 스키마를 흔드는 것은 **채점표를 고치는 일**에 가깝다.
> 과제 REPORT 2번이 묻는 "**뽑지 않기로 한 관계와 그 대가**" 가 정확히 이것이므로,
> 지도 화면과 REPORT 에 한계로 싣는다.

### Place(지역)를 넣지 않는다

한양·만주·상하이는 거의 모든 인물에 붙어서 차수가 폭발하고, 그 지역을 지나는 경로는
"같은 곳에 있었다" 이상을 말하지 못한다.
**뽑지 않기로 한 관계와 그 대가는 REPORT 에 적는다** (과제 요구 항목).

### 관계 6종 — 방향이 의미를 가진다

| 관계 | from → to | 근거가 되는 서술 |
|---|---|---|
| `PARTICIPATED_IN` | Person → Event | "3·1 운동에 참여하였다" |
| `FOUNDED` | Person → Organization | "신민회를 조직하였다" |
| `MEMBER_OF` | Person → Organization | "의열단에 가입하였다" |
| `LED` | Person → Organization/Event | **장(長)·대표·지휘자였다는 서술만** — "임시정부 주석을 맡았다" |
| `AFFECTED` | Event → Organization | **조직이 해산·탄압·수립·분열됐다고 명시한 경우만** — "105인 사건으로 신민회가 해체되었다" |
| `STUDIED_UNDER` | Person → Person (**from=제자, to=스승**) | "안창호는 이승훈의 문인이다" → from 안창호, to 이승훈 |

**`RELATED_TO`(Organization ↔ Event) 를 버리고 `AFFECTED`(Event → Organization) 로 바꿨다.**
표 제목이 "방향이 의미를 가진다" 인데 이 하나만 무방향이었고, 이름도 아무 말을 하지 않았다.
근거로 든 문장("105인 사건으로 신민회가 해체되었다")은 실은 **사건이 조직에 한 일**이다.
방향을 박으면 "신민회를 무너뜨린 사건은?" 과 "105인 사건이 무너뜨린 조직은?" 이
서로 다른 질문으로 갈린다.

> **대가**: 반대 방향(조직이 사건을 일으킴 — 신민회 → 105인 사건)을 못 담는다.
> 관계를 7종으로 늘리는 대신 **한 방향만 뽑고 그 대가를 REPORT 2번에 적는다**
> (과제가 "뽑지 않기로 한 관계와 그 대가" 를 명시적으로 묻는다).

`MEMBER_OF` 와 `LED` 를 나눈 이유 — "가입했다" 와 "이끌었다" 는 질문이 다르다.
한 관계로 뭉치면 "임시정부를 이끈 사람" 에 단원 전원이 딸려 온다.

학맥은 조선시대에서 특히 중요하다. 이익 → 정약용 같은 사제 관계가 조선 후기 인물을
잇는 **가장 굵은 다리**이고, 이것이 없으면 조선 쪽 2홉 질문이 거의 만들어지지 않는다.

#### `MENTORED` 를 `STUDIED_UNDER` 로 바꾼 이유 — **내가 방향을 정의하지 않았다**

처음엔 이렇게 적었다.

```
| MENTORED | Person → Person | "정약용은 성호 이익의 학문을 이었다" |
```

**이름과 예시가 서로 반대다.** `MENTORED` 는 "A가 B를 가르쳤다" 이니 스승→제자인데,
예시는 정약용(제자)이 먼저 나온다. 모델이 둘 사이를 오갔다 — 1차 추출 518건 중
**방향 판별이 가능한 18건에서 14건(77%)이 역방향**이었고, 39%는 근거 문장에 사제
관계 어휘조차 없었다.

`STUDIED_UNDER`(제자가 스승 **밑에서 배웠다**)로 바꾸면 **이름이 방향을 말한다.**
프롬프트에 판정 문장도 박았다 — *"학문·사상을 배운 관계만. 권유·소개·천거·동료·
교유는 제외"*, 그리고 *"A의 학문이 B로 이어졌다 는 A가 스승이다"*.

> **교훈**: 관계 이름은 방향을 담아야 한다. `MENTORED` 는 읽는 사람마다 다르게 읽히고,
> **모델도 그렇게 읽는다.** 이름으로 못 박을 수 있는 것을 주석으로 설명하려 들면
> 문서 140건에 걸쳐 제각각이 된다.

### LLM 추출 — 지어내기를 코드로 막는다

문서 하나를 주고 **스키마 안의 관계만** 뽑게 한다. 모델은 `gpt-4.1-mini`.
반드시 함께 내게 하는 것이 하나 있다.

```json
{ "from": "안창호", "to": "신민회", "kind": "FOUNDED",
  "quote": "1907년 국내로 들어와 신민회를 조직하였다." }
```

#### 문서 하나를 통째로 넣지 않고 조각낸다

수집하고 나서 잰 코퍼스는 **총 328만 자, 문서 평균 23,419자, 최대 139,542자**다.
"문서 하나 = 요청 하나" 로 두면 걸리는 게 둘이다.

| | |
|---|---|
| **재현율이 조용히 샌다** | 입력이 길수록 뒷부분 관계를 놓친다. `quote` 대조는 **지어낸 것**을 잡지 안 뽑은 것은 못 잡는다. 손실이 숫자에 안 보인다 |
| **되돌릴 단위가 크다** | 한 건 실패에 2만 자를 통째로 다시 돌린다 |

그래서 **문단 경계에서 6,000자 안팎으로 조각내** 조각마다 추출한다. 약 550회 호출이
되지만 총 토큰(≈164만)은 같고, 조각마다 모델이 좁게 본다. 실패 단위도 작아진다.

> **앞부분만 자르는 선택지는 버렸다.** 그러면 생애 후반 관계 — 안창호의 임시정부
> 활동 같은 것 — 이 통째로 빠진다. 코퍼스를 140건이나 모은 이유가 없어진다.

조각 경계에 걸친 관계는 놓칠 수 있다. **그 대가를 REPORT 에 적는다.**

**`quote` 가 원문에 그대로 있는지 코드가 대조한다.** 없으면 그 엣지를 버린다.
모델이 아는 역사 지식으로 채운 관계는 이 대조를 통과하지 못한다.
**통과율을 숫자로 보고한다** — 몇 %가 걸러졌는지가 이 방어막이 실제로 일했다는 증거다.

#### 원문 대조만으로는 절반밖에 못 막는다 (스모크 테스트에서 드러남)

《안창호》 한 건으로 먼저 돌려 보고 눈으로 읽었더니, 통과율 83% 라는 숫자 뒤에
이런 것들이 섞여 있었다.

```
✗ (안창호) ─MENTORED─▶ (이광수)
    "장택상은 그를 대통령이 될 자질을 갖춘 인물이라고 평가했다…"
    → 문장은 원문에 실재한다. 그런데 그 관계를 말하지 않는다

✗ (안창호) ─MENTORED─▶ (대한민국 임시정부)
    → MENTORED 는 Person → Person 인데 to 가 조직이다

✗ (안창호) ─LED─▶ (흥사단)
    "그의 장례식은 흥사단과 수양동지회 회원의 주도로 거행되었고"
    → 장례식을 흥사단이 주도한 것이지 그가 이끈 것이 아니다
```

**`quote` 대조는 "그 문장이 실재하는가" 만 보고 "그 문장이 그 관계를 말하는가" 는
못 본다.** 방어막을 둘 더 댔다.

| 방어막 | 무엇을 막나 | 오탐 |
|---|---|---|
| **타입 서명 대조** (코드) | 관계마다 양쪽 노드 타입을 고정 — `MENTORED` 의 to 가 조직이면 버린다. 모델이 `fromType`·`toType` 을 같이 내게 했다 | 없음 |
| **프롬프트 조항 1-1** | *"quote 는 그 관계를 **직접 서술**하는 문장이어야 한다. 두 개체가 같은 문장에 나온다고 관계가 있는 것이 아니다. 없으면 엣지를 내지 마라"* | 없음 |

같은 문서를 다시 돌리니 **제안 58 → 33개, 통과율 83 → 88%** 로 바뀌었다. 모델이
보수적으로 바뀌어 수가 줄었는데, **읽어 보니 줄어든 쪽이 맞았다** — 14건을 훑어
명백한 오류가 1건으로 떨어졌다.

> **버린 방어막도 적어 둔다.** "quote 안에 from·to 이름이 둘 다 나올 것" 을 재 봤더니
> 48개 중 **10개(20%)만 살아남았다.** 표기 변형 때문이다 — 《대한민국 임시정부》를
> 본문은 "임시정부" 라 쓰고, 주어는 "그가" 로 받는다. 정당한 엣지를 대량으로 버리는
> 필터라 **쓰지 않기로 했다.** 그 문제는 §5 정제가 푼다.

**남은 오류는 숫자로 보고한다.** 코드로 다 막을 수 없다는 것이 이 단계의 결론이고,
표본을 손으로 읽어 오류율을 재서 §7 의 실패 분석에 싣는다.

#### 전량 추출 실측 — 두 번 돌렸다 (2026-09-21)

| | 1차 | 2차 (스키마 교정 후) |
|---|---|---|
| 제안 → 채택 | 2,948 → 2,430 (**81%**) | 2,937 → 2,256 (**77%**) |
| 버림 | 근거 없음 331 · **타입 불일치 197** · 스키마 밖 19 | 근거 없음 175 · **타입 불일치 506** |
| 비용·시간 | $1.44 · 9분 38초 | $1.63 · 9분 23초 |

```
관계 분포가 재배치됐다
  LED              921 → 700  (-24%)    정의를 조이자 줄었다
  MEMBER_OF        552 → 685  (+24%)  ┐ 잘못 LED 로 가던 것이
  PARTICIPATED_IN  209 → 375  (+79%)  ┘ 제자리를 찾았다
  MENTORED 518 → STUDIED_UNDER 184 (-64%)   친구·교유가 걸러졌다
```

**표본을 손으로 읽어 잰 관계별 정확도** (각 5~8건):

| 관계 | 1차 | 2차 |
|---|---|---|
| `MEMBER_OF` | 6/7 | — (양호) |
| `LED` | 3/8 (38%) | **5/8 (63%)** |
| `AFFECTED` | 2/19 (10%) | **3/6 (50%)** |
| `MENTORED`→`STUDIED_UNDER` | ~1/16 (15%) | **2/6 (33%)** |

> **3차를 돌리지 않았다.** 남은 오류가 두 종류로 갈렸기 때문이다 —
> ① 관직(`국회 부의장`)·한국사 밖(`마오쩌둥`)은 **코드로 확실히 잡힌다**. 프롬프트로
> 세 번 말해도 새는 것이라 §5 로 넘겼다. ② `세종대왕→정몽주`(실제 스승은 권우)처럼
> 근거를 잘못 읽은 의미 오류는 몇 번을 돌려도 일정 비율 남는다.
> **$1.6 을 더 쓰기보다 남은 오류율을 정직하게 재서 보고하는 편이 낫다** — 루브릭 3이
> 요구하는 것이 그것이다. 1차 결과는 `edges.raw.v1.jsonl` 로 보존해 전후를 대조한다.

(영화에서 쓴 것과 같은 원칙 — 근거에 없으면 말하지 않는다. 여기서는 추출 단계에 적용한다.)

## 5. 정제·병합 (과제 필수 단계)

| 문제 | 실제 사례 | 조치 |
|---|---|---|
| **호·시호·이명이 다른 노드가 된다** | 세종 = **세종대왕** = 이도 · 정약용 = **다산** · 김구 = **백범** · 이순신 = **충무공** | 위키백과 `redirects` 와 본문 첫 문단의 한자·호를 별칭으로 모아 **본명 하나로 병합** |
| **표기 흔들림** | `3·1 운동` / `3.1운동` / `삼일운동` · `5·18` / `오일팔` | 중점·마침표·공백을 턴 뒤 대조 |
| **일반명사가 노드가 된다** | `독립` · `개혁` · `학교` · `정부` | 일반명사 사전으로 제외. 사전은 **추출 결과에서 빈도로 뽑아** 만든다 (추측으로 목록을 쓰지 않는다) |
| **관직이 조직이 된다** | `전라도관찰사` · `삼도수군통제사` · `국회 부의장` · `외무참의` | 관직은 **자리**이지 조직이 아니다. 접미사 사전으로 제외 — 추출 결과에서 44개 노드가 걸렸다. 프롬프트로 세 번 말해도 새서 **코드로 막는다** |
| **한국사 밖이 섞인다** | `마오쩌둥` · `문화 대혁명` · `십자군 전쟁` · `도요토미 히데요시` | 목록으로 제외. **정규식으로 "외국" 을 잡으려다 `김일성`(62엣지)·`김정일` 을 버릴 뻔했다 — 북한사는 한국사다.** 그래서 목록으로 둔다 |
| **직함이 이름에 붙는다** | `김대중 대통령` · `김정일 국방위원장` | 접미사를 떼어 본명으로 합친다 |
| **동명이인** | 김구(백범) vs 다른 김구 · 여러 '이순신' | 생몰년·분류로 구분. 구분 못 하면 **합치지 않고 남겨 두고 리포트에 찍는다** |
| **허브가 지름길을 만든다** | 실측 차수 상위 — `조선`132 · `김구`67 · `미국`66 · `이승만`66 · `일제강점기`66 · `박정희`61 | 탐색에서 **통과 금지**. 목적지로는 되지만 경유는 막는다. `조선` 이 2위의 두 배라 **끊는 자리가 눈에 보인다** |
| **같은 관계 중복** | 여러 문서가 같은 사실을 서술 | `from·to·kind` 로 중복 제거, `quote` 는 여러 개 보관 |

> 병합 기준을 세웠다는 것을 **숫자로 보인다** — 병합 전후 노드 수, 별칭으로 합쳐진
> 건수, 일반명사로 버린 건수, 동명이인으로 남겨 둔 건수를 빌드 리포트에 찍는다.
> 루브릭의 "같은 개체를 하나로 합치는 기준을 세웠는가" 가 이 숫자로 답해진다.

#### 돌리고 나서 (2026-09-21, `scripts/history/build-graph.ts`)

```

  버림       관직 32 · 한국사 밖 21 · 너무 짧음 6
  중복 병합   2,197 → 1,620개  (577개 합쳐짐)
  노드       1,221 → 1,135개  (86개 별칭으로 합쳐짐)
  별칭 출처   리다이렉트 12 · 호(號) 69 · 표기 변형 26
  타입 갈림   4개 (다수결) · 동명이인 의심 0개
```

**호(號)가 리다이렉트보다 훨씬 많이 합쳤다** — 위키백과 리다이렉트는 12건뿐인데
본문 첫 문단에서 뽑은 호가 69건이다. `백범`→김구 · `우남`→이승만 · `몽양`→여운형 ·
`도산`→안창호 · `해공`→신익희 · `완당`→김정희. **본문에서 뽑기로 한 것이 주효했다.**

> **첫 실행에서 버그가 하나 나왔다.** 정규화하면 같은 키인데 따로 남은 노드가 20쌍
> 있었다 — `신한청년당`/`신한 청년당`, `대한인국민회`/`대한인 국민회`,
> `3.1 만세 운동`/`3·1 만세 운동`. **정규화를 정본(문서 제목) 대조에만 쓰고 정본 밖
> 이름끼리는 안 묶은** 탓이다. 같은 키끼리 모아 가장 많이 쓰인 표기를 대표로 세우게
> 고쳐 0건이 됐다.

#### 그래프가 실제로 서는지 — 확인했다

```
연결 요소 44개 · 최대 1,015개(89%) · 다리 후보 120개

안창호 ↔ 신민회    직접연결 O · 공통이웃 2 (이승훈, 윤치호)
김구  ↔ 임시정부    직접연결 O · 공통이웃 4 (김규식, 여운형, 3·1 운동, 이승만)
```

**롱테일이 크다.** 노드 1,135개 중 **807개(71%)가 차수 1**이고, 문서를 가진 노드는
112개뿐이다. 평균 차수가 2.4로, 1.5 단계 언급 그래프(27.6)와 크게 다르다 —
당연하다. **언급은 흔하고 명시적 관계 서술은 드물다.** §3 이 "언급 그래프는 엣지 수의
상한" 이라고 한 것이 그대로 확인됐다.

탐색에 실제로 쓰이는 것은 **차수 2 이상인 328개**이고 그중 문서를 가진 112개가
중심이다. **골든셋 40문항은 이 중심부에서 만든다**(§7).

### 선택 — 외부 인물 API 로 별칭·동명이인을 검증한다 (지금은 하지 않는다)

위 표에서 약한 칸이 둘이다. **호·시호 병합**은 위키백과 첫 문단을 정규식으로 긁는
것이라 놓치는 게 생기고, **동명이인**은 "구분 못 하면 합치지 않는다" 로 사실상 미룬
상태다. 이 둘에는 쓸 만한 외부 소스가 실재한다 (2026-09-21 확인).

| 소스 | 주는 것 | 커버리지 |
|---|---|---|
| [한국역대인물 종합정보시스템](https://www.data.go.kr/data/15052748/fileData.do) (한국학중앙연구원 OpenAPI) | **자(字)·호(號)·시호(諡號)·본관·생몰년**이 필드로 | 고려·**조선 중심** |
| [독립유공자 공훈록](https://www.data.go.kr/data/15057718/openapi.do) (국가보훈부) | 공적조서·공훈록 | **구한말·일제만** |

**코퍼스 소스로는 쓰지 않는다.** 이것이 중요하다 — 인물사전은 **이미 구조화된
데이터**다. 코퍼스에 섞으면 그 부분은 규칙으로 뽑게 되고, §1 이 "이번에는 산문이라
LLM 추출이 필요하다" 고 한 전제가 그만큼 무너진다. **TMDB 상황이 재현되는 것**이고,
과제가 요구한 `①추출 → ②정제·병합` 이 다시 안 드러난다.

두 번째 이유는 **시대 편향**이다. 두 API 를 합쳐도 해방·현대는 비어 있다. 지금 있는
시대별 밀도 차이(§11)를 줄이는 게 아니라 **키운다** — "조선만 잘 나오는데 소스가
달라서" 는 §7 의 시대별 표를 해석 불가능하게 만든다.

세 번째는 **인증키**다. 공공데이터포털은 회원가입과 키 신청이 필요하다.
§9 의 "clone 만으로 뜬다" 에 문턱이 하나 더 붙는다.

> **그래서 쓴다면 §5 안에서만 쓴다** — 코퍼스가 아니라 **별칭 사전과 동명이인
> 판별의 검증 소스**로. 이것은 관계 추출을 대신하는 게 아니라 정제를 받치는 것이라
> 과제 ② 단계를 **약화시키지 않는다.** REPORT 에는 "별칭 병합을 외부 권위 소스로
> 대조했다" 가 근거로 남는다.
>
> **다만 지금은 하지 않는다.** §11 의 "범위가 과제 최소를 크게 넘는다" 가 이미
> 올라와 있다. **필수를 다 끝낸 뒤 시간이 남으면**, 조선 인물 별칭에 한정해 붙인다.

## 6. 탐색과 답변

탐색은 **이 도메인에 맞춰 새로 짠다.** `Person · Organization · Event` 가 전부
노드이면서 **전부 근거**다 — "안창호가 참여한 사건" 에서 사건은 다리가 아니라 답 자체다.
한 타입만 결과에 담는 이분 구조와는 루프 모양이 다르다. 맞춰 가져가는 것은
`Hop · Collected · Budget` **타입 모양**뿐이다.

```
질문 → ① 씨앗 찾기 ── 문서 제목 대조 → 별칭 대조 → BM25 (순서대로, 앞이 실패하면 뒤로)
     → ② n홉 확장 ── 관계별 예산, 허브 통과 금지, 방문한 홉을 전부 기록
     → ③ 근거 조립 ── 삼중항 + 근거 문장 + 출처 문서
     → ④ 답변      ── 근거에 있는 것만. 없으면 "확인되지 않습니다"
```

### 홉 상한과 허브 회피 — 기준과 그 이유를 남긴다 (과제 요구)

**재고 나서 붙였다** (6단계 · `output/history/hop-sweep.json` · `tuned` 20문항).
**holdout 18문항은 보지 않았다** — 보고 고르면 홀드아웃이 홀드아웃이 아니게 된다.

| 결정 | 확정값 | 실측 근거 |
|---|---|---|
| 최대 홉 | **2** | 컨텍스트 재현율 80→**95**→95→95%, 경로 재현율 56→**63**→63→63%. **2에서 두 지표가 다 포화**하고, 3은 근거만 45→54로 키운다 |
| 근거 노드 상한 | **80** | 3홉 문항 재현율 20건:0/3 · 40건:1/3 · **80건:3/3** · 160건:3/3. **여기가 진짜 병목이었다** |
| 관계당 상한 | **12** | 80→90→**95**→95→95%. 24·48은 근거만 54→69로 커진다 |
| 허브 통과 금지 | **8** (근거 약함) | n=0·2·4·8·16 이 **전부 85%로 같았다.** 32에서만 80%로 나빠진다 |

> **허브 차단은 효과가 드러나지 않았다.** 설계서는 허브가 "지름길을 만든다" 고 보고
> 이 장치를 넣었는데, **재현율이 아무 차이를 보이지 않았다.** 이 골든셋에 허브를
> 지나야만 닿는 문항이 없었기 때문으로 보인다. 과하게 올리면(32) 나빠지는 것만
> 확인됐으므로 8만 남긴다. **근거가 약한 결정이라는 것을 REPORT 에 그대로 적는다** —
> 효과를 못 보였는데 "허브를 막아 정확도를 지켰다" 고 쓰면 거짓이다.

> **처음 진단이 틀렸다.** 5단계 스모크에서 3홉 5문항을 놓쳤을 때 "허브 차단이 과한
> 것 같다" 를 1순위로 의심했다. 재 보니 **근거 예산**이었다. 원인 후보가 여럿일 때
> 짐작으로 고르지 않고 스윕을 단계로 둔 이유가 이것이다.

> **경로 재현율 63%는 낮다.** 기대 홉의 37%가 실제 탄 경로에 없다. 예산을 늘려도
> 안 오르므로 탐색 문제가 아니다 — 기대 경로의 표기가 그래프와 다르거나, 탐색이
> 다른 길로 도달한 것이다. **7단계 실패 분석에서 읽어 가른다.**

### LLM 을 부르는 곳

**답변 문장 생성 한 곳뿐이다.** 탐색·씨앗 찾기·조립에는 LLM 이 한 줄도 없다.
덕분에 평가가 **LLM 호출 0회, 비용 0원**으로 돌아간다 — 하루에 몇 번이고 다시 잰다.
(관계 추출은 빌드 시점에 한 번만 LLM 을 쓴다. 질의 경로가 아니다.)

### 파이프라인 — 두 도메인이 **한 그래프**를 쓴다 (과제 REPORT 4번)

과제는 REPORT 에 **"LangGraph 노드 및 상태(State) 흐름"** 의 **전체 아키텍처**
다이어그램을 요구한다. REPORT 가 영화·인물을 함께 다루므로(§9), 그림도 하나여야 한다.

질의 처리는 도메인과 무관하게 단계가 같다 — 라우팅 → 씨앗 → n홉 확장 →
거절 게이트 → 조립 → 답변. 갈림길도 셋이다(범위 밖 · 씨앗 없음 · 근거 부족).
**다른 것은 각 단계의 속이지 순서가 아니다.**

그래서 **`StateGraph` 정의를 하나만 두고 노드 구현을 도메인이 주입**한다.
그래프 모양·노드 이름·엣지 조건은 공유하고, `route`/`seeds`/`expand`/`assemble`
안에서 무슨 일이 일어나는지만 갈린다.

> **이 구조 자체가 REPORT 의 논지다.** "같은 엔진에 성질이 정반대인 두 코퍼스를
> 물렸다" 를 **그림 한 장으로 증명**한다. 도메인마다 그래프를 따로 그리면
> 그 대조가 사라진다.

직접 State 머신을 짜는 대신 진짜 LangGraph 를 쓰는 이유는 하나다 —
**과제가 요구한 것을 대응표로 변명하지 않고 문자 그대로 충족한다.**

```
                    START
                      │
                  ┌───▼────┐
                  │ route  │  질문 종류 판정 · 범위 밖 판정
                  └───┬────┘
                      │ out_of_scope ──────────────┐
                  ┌───▼────┐                       │
                  │ seeds  │  제목 → 별칭 → BM25    │
                  └───┬────┘                       │
                      │ 씨앗 없음 ─────────────────┤
                  ┌───▼────┐                       │
                  │ expand │  n홉 확장 · 허브 통과 금지
                  │        │  **탄 경로를 State 에 쌓는다**
                  └───┬────┘                       │
                      │ 근거 부족 ─────────────────┤
                  ┌───▼─────┐                 ┌────▼────┐
                  │ assemble│ 삼중항·근거·출처 │ refuse  │
                  └───┬─────┘                 └────┬────┘
                  ┌───▼────┐                       │
                  │ answer │  LLM 1회 — 여기뿐      │
                  └───┬────┘                       │
                      └───────────┬────────────────┘
                              ┌───▼────┐
                              │ record │  runs.jsonl 에 append
                              └───┬────┘
                                 END
```

`followup` 은 **도메인이 지원할 때만** 갈라진다. 영화는 "그중에 2010년 이후는?"
같은 이어지는 질문을 이미 받고, 인물은 아직 안 받는다 — **안 받는 도메인은
조건이 항상 `route` 로 떨어진다.** 노드를 지우는 대신 이렇게 두면 그래프가 하나로 남는다.

State 는 노드마다 한 칸씩 채워지고, **채우는 칸은 같고 채우는 방법이 다르다.**

| 노드 | State 에 채우는 것 | 🎬 영화 구현 | 🏛 인물 구현 | LLM |
|---|---|---|---|---|
| `followup` | `followUp` | 직전 근거 필터 | (없음 — 통과) | 0 |
| `route` | `routeKind` · `reason` | 배역·수상·장르·교집합 판정 | 인물·조직·사건 판정 | 0 |
| `seeds` | `seedIds` | 제목 → 인물 → 배역 → BM25 | 제목 → 별칭 → BM25 | 0 |
| `expand` | `evidence` · **`path`** | 영화 → 인물 → 영화 (**인물은 다리**) | Person·Org·Event (**전부 근거**) | 0 |
| `assemble` | `triples` · `quotes` · `sources` | 크레딧 + 줄거리 | 삼중항 + `quote` 원문 | 0 |
| `answer` | `answerText` | 근거만으로 | 근거만으로 | **1** |
| `refuse` | `refused` · `refusalReason` | 공통 | 공통 | 0 |
| `record` | — (`runs.jsonl` 에 append) | 공통 | 공통 | 0 |

**`expand` 행이 두 도메인의 차이 전부다.** 영화는 이분 그래프라 인물이 다리로만
쓰이고 결과엔 영화만 담긴다. 인물 그래프는 세 타입이 전부 노드이자 전부 근거다.

```ts
// lib/pipeline.ts   — 도메인 무관. API 는 @langchain/langgraph 1.4.16 문서로 확인함
//                     (v1 부터 Annotation.Root 가 아니라 StateSchema + zod 다)
import { StateGraph, StateSchema, START, END } from "@langchain/langgraph";
import { z } from "zod/v4";

/** 도메인이 채워 넣는 것 — 그래프 모양은 건드리지 못한다 */
export interface Domain {
  name: "movie" | "history";
  followUp?: (s: Ask) => Partial<Ask>;      // 없으면 followup 노드는 통과
  route:     (s: Ask) => Partial<Ask>;
  seeds:     (s: Ask) => Partial<Ask>;
  expand:    (s: Ask) => Partial<Ask>;      // path 를 여기서 쌓는다
  assemble:  (s: Ask) => Partial<Ask>;
  answer:    (s: Ask) => Promise<Partial<Ask>>;
}

// **State 키가 노드 이름과 같으면 LangGraph 가 거부한다** (구현하다 부딪혔다).
// route·seeds·answer 가 겹쳐서 State 쪽 이름을 바꿨다 — REPORT 다이어그램에
// 나가는 것은 노드 이름이므로 그쪽을 지켰다.
const askFields = {
  question:   z.string(),
  routeKind:  z.string().default(""),                  // 노드 `route` 가 채운다
  seedIds:    z.array(z.string()).default([]),         // 노드 `seeds`
  path:       z.array(z.custom<Hop>()).default([]),    // **탄 경로**
  evidence:   z.array(z.custom<Evidence>()).default([]),
  triples:    z.array(z.custom<Triple>()).default([]),
  sources:    z.array(z.string()).default([]),
  answerText: z.string().nullable().default(null),     // 노드 `answer`
  refused:    z.boolean().default(false),
  trace:      z.array(z.string()).default([]),         // 지나온 노드 이름
};
const Ask = new StateSchema(askFields);

export const build = (d: Domain) => new StateGraph(Ask)
  .addNode("followup", d.followUp ?? ((s) => ({})))
  .addNode("route",    d.route)
  .addNode("seeds",    d.seeds)
  .addNode("expand",   d.expand)
  .addNode("assemble", d.assemble)
  .addNode("answer",   d.answer)
  .addNode("refuse",   () => ({ refused: true }))
  .addNode("record",   (s) => record(d.name, s))       // runs.jsonl
  .addEdge(START, "followup")
  .addConditionalEdges("followup", (s) => s.followUp ? "record" : "route", ["record","route"])
  .addConditionalEdges("route",    (s) => s.routeKind === "out_of_scope" ? "refuse" : "seeds", […])
  .addConditionalEdges("seeds",    (s) => s.seedIds.length ? "expand" : "refuse", […])
  .addConditionalEdges("expand",   (s) => s.evidence.length ? "assemble" : "refuse")
  .addEdge("assemble", "answer")
  .addEdge("answer", "record").addEdge("refuse", "record").addEdge("record", END)
  .compile();

// lib/domains/movie.ts   · lib/domains/history.ts
//   기존 순수 함수를 그대로 호출해 Domain 을 채운다. 로직은 옮기지 않는다.
```

**얻는 것 넷.** ① 다이어그램이 코드에서 그대로 나오고, **두 도메인이 그림 한 장**을
공유한다(요구 4번). ② 거절이 `if` 조기 리턴이 아니라 **이름 있는 노드**가 되어
"어디서 끊겼는지" 가 `runs.jsonl` 에 남는다. ③ §7 의 실패 3층이 노드 이름과
**1:1 로 맞는다** — `seeds` 에서 죽으면 색인, `expand` 면 탐색, `answer` 면 생성이다.
④ 한쪽에서 고친 흐름이 **양쪽에 동시에 적용된다** — 예컨대 `record` 는 한 번 붙이면
두 도메인이 같이 로그를 남긴다.

**치르는 대가도 적는다.** 런타임 의존성이 `@langchain/langgraph` + `@langchain/core`
+ `zod` 로 셋 늘어난다 (지금은 next·react·three 뿐이다). 그리고 이 규모에서
LangGraph 의 진짜 강점 — 체크포인트 후 재개, 사이클, human-in-the-loop, 스트리밍 —
은 **하나도 쓰지 않는다.** 쓰는 것은 노드·조건부 엣지·State 셋뿐이다.
**REPORT 에 이대로 적는다. 안 쓰는 기능으로 포장하지 않는다.**

> **평가는 여전히 LLM 0회다.** `answer` 노드를 빼고 컴파일한 그래프를 `evaluate.ts`
> 가 돌린다. LangGraph 는 실행 엔진일 뿐 LLM 과 무관하다.

#### 구현하고 나서 (2026-09-21, `lib/pipeline.ts` · `lib/domains/history.ts`)

돌려 보니 예상 못 한 것이 둘 나왔다.

**① LangGraph 는 노드 이름과 State 키가 같으면 거부한다.** `route`·`seeds`·`answer`
셋이 겹쳤다. 다이어그램에 나가는 것은 노드 이름이므로 **State 쪽을 바꿨다** —
`routeKind` · `seedIds` · `answerText`.

**② 삼중항에 정렬이 없었다.** "안창호가 세운 조직은?" 의 근거 상위가 전부 **김구**로
나왔다. 그래프에 담긴 순서대로 뽑았기 때문이다. **씨앗에서 가까운 홉 순**으로,
같으면 근거 문장이 많은 것부터(여러 문서가 말한 사실) 정렬하게 고쳤다.

**`trace` 가 실패 3층 분류를 공짜로 준다.** 노드에 이름이 있으니 어디서 끊겼는지가
그대로 남는다 — `route` 에서 끊기면 범위 밖, `seeds` 면 색인, `expand` 면 탐색,
`answer` 까지 가고도 틀리면 생성이다. §7 이 따로 추론할 필요가 없어졌다.

```
질문   오늘 서울 날씨 어때?
경유   followup → route → refuse          ← 이 한 줄이 층 분류다
```

단위 테스트 9건으로 세 가지를 지킨다 — **경로가 기록되는가**(역방향 홉 포함),
**허브를 경유하지 않는가**(목적지로는 허용), **근거가 없으면 거절하는가**.
영화 쪽 64건도 같이 돌려 **아직 손대지 않았음**을 확인했다.

### 영화 쪽을 공통 그래프에 올릴 때 — 회귀를 숫자로 막는다

영화의 `ask()` 는 이미 순수 함수들을 순서대로 부르고 있어서, **노드가 그 함수를
그대로 호출**하면 된다. 로직을 옮기거나 고치지 않는다 — **감싸기만 한다.**

그래도 1,400줄 가까운 동작하는 코드를 건드리는 일이다. 그래서 순서를 못 박는다.

```
① 인물 쪽에서 공통 그래프를 먼저 완성한다 (새 코드라 깨져도 잃을 게 없다)
② 영화 평가셋 152문항을 전환 전에 돌려 숫자를 박아 둔다   ← 기준선
③ 영화 도메인을 공통 그래프에 얹는다
④ 같은 152문항을 다시 돌려 **숫자가 한 칸도 안 움직였는지** 확인한다
   움직이면 전환을 되돌린다. 리팩터링이 성능을 바꿨다면 그것은 리팩터링이 아니다
```

`data/golden.json` 에 6묶음 152문항이 있고 그중 `holdout-100` 은 동결 후 채점용이다.
**기준선이 이미 있다는 것이 이 전환을 시도할 수 있는 유일한 이유다.**

## 7. 평가 설계 — 루브릭이 가장 무겁게 보는 곳

### 골든셋 40문항 이상

| 필드 | 내용 | 과제 요구 |
|---|---|---|
| `question` | 질문 | |
| `answer` | 기대 정답 | ✅ 기대 정답 |
| `hops` | **1 · 2 · 3** | ✅ 홉 수별 보고의 근거 |
| `path` | `안창호 ─FOUNDED─▶ 신민회 ─RELATED_TO─▶ 105인 사건` | ✅ **기대 경로(관계·순서·방향)** |
| `quote` | 원문 근거 문장 | ✅ 원문 근거 |
| `expected` | 근거로 와야 할 문서 | 재현율 계산용 |
| `era` | 조선 전·중기 / 조선 후기 / 구한말·일제 / 해방·현대 | 시대 쏠림 확인 |
| `split` | `tuned` / `holdout` | 과적합 분리 |
| `type` | `answerable` / `refusal` | **거절 문항에는 기대 경로·근거가 없다.** 이 칸이 없으면 필수 필드 검증이 거절 8문항에서 깨진다 |

문항 구성 — **1홉만 채우면 멀티홉을 증명하지 못한다.**

```
1홉  10문항   "세종이 세운 기관은?"
2홉  14문항   "안창호가 참여한 사건에 같이 있던 인물이 세운 조직은?"
3홉   6문항   "A가 이끈 조직이 관련된 사건에 참여한 다른 인물은?"
시대 교차 4문항  "정약용의 학맥을 이은 사람이 참여한 개혁은?"  ← 얇을 것으로 예상. 한계 확인용
거절  8문항   범위 밖(주가·날씨) + 남의 도메인(영화 질문)

── 나중에 추가 ──────────────────────────────────────────
bridge-hard 10문항   **BM25 가 원리적으로 못 푸는 것만.**
                     답의 근거 문서에 질문 개체 이름이 한 번도 안 나온다.
                     기존 묶음에서 BM25 가 이긴 뒤 원인을 진단해 만들었다.
```

**최종 52문항** — 1홉 10 · 2홉 27 · 3홉 7 · 거절 8. 묶음은 tuned 20 · holdout 14 ·
bridge-hard 10 · 거절 8.

**시대 교차 문항을 일부러 넣는다.** 600년으로 넓힌 대가가 여기서 드러날 것이다.
못 맞히면 그 숫자를 그대로 싣는다 — **잘하는 자리만 재면 도구를 과대평가하게 된다.**

> **전제가 하나 흔들렸다.** 1.5 단계 실측에서 시대 교차 언급이 1,185개로, 내부
> 합계(1,328)와 맞먹었다(§3). "시대 교차는 얇아서 못 맞힐 것" 이라는 예상이
> 틀렸을 수 있다. **그래도 문항은 그대로 넣는다** — 예상이 맞든 틀리든 재야 알고,
> 틀린 예상을 지우는 것보다 **틀렸다고 보고하는 편이 낫다.**

### 재는 것 셋

| 무엇 | 어떻게 | LLM |
|---|---|---|
| **컨텍스트 재현율** | 기대 문서가 근거에 들어왔는가 | 0회 |
| **경로 재현율** | 기대 경로의 관계가 실제 탄 경로에 있는가 | 0회 |
| **답변 정확도** | 근거가 맞을 때 답도 맞는가 | 문항당 1회 (캐시) |

**세 번째 층을 반드시 만든다.** 영화에서 근거 12편이 완벽한데 답변만 고장난 적이
있었고 그때 재현율은 **한 칸도 안 움직였다.** 안 재는 층에서 나는 고장은 숫자로 안 잡힌다.

#### 실측 — 이 층을 안 쟀으면 28%p 를 못 봤다 (7.2단계)

```
          컨텍스트 재현율   답변 정확도
  1홉          100%           80%
  2홉           93%           67%
  3홉           57%           14%
  전체          89%           61%     ← 28%p 격차
  거절         100%          100%
```

**근거는 89% 데려오는데 답변은 61% 다.** 재현율만 적었으면 그만큼 부풀려 말했을 것이다.

#### 원인을 세 번 짚어 두 번 틀렸다

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| ① 근거가 157개라 묻혔다 | `maxNodes` 10/20/40/80 스윕 | ❌ **답변 정확도가 평평했다** (43~50%) |
| ② 탄 경로를 프롬프트에 안 줬다 | 경로를 근거 블록에 추가 후 재측정 | ❌ 50% 그대로 |
| ③ **근거가 30개에서 잘렸다** | 답이 든 삼중항의 위치를 추적 | ✅ **90번째** — 모델은 답을 본 적이 없다 |

```
h2-07  "1948년 김규식이 참여한 협상에 함께 참여한 인물은?"
       (김구) ─참여─▶ (남북협상)   ← 138개 중 90번째
       evidenceBlock(limit = 30)    ← 앞 30개만 전달
       모델: "근거에서 확인되지 않습니다"
```

고친 뒤 **전체 50%→61%, 2홉 48%→67%, "확인되지 않습니다" 12건→6건.**

> **①이 평평했던 이유도 이것이었다.** `maxNodes` 를 40이든 80이든 올려도 **30에서
> 잘려** 모델에게 가지 않았다. 근거를 더 모아도 전달이 안 되니 스윕이 아무것도
> 못 본 것이다. **한 지표가 둔감할 때 "영향 없음" 으로 읽으면 안 된다 —
> 그 사이에 막힌 데가 있는지 먼저 봐야 한다.**

> ②는 효과가 0이었지만 **되돌리지 않았다.** 경로 제시는 루브릭 2가 요구하는 것이고,
> **효과가 없는 것과 틀린 것은 다르다.**

### 홉 수별 보고 (루브릭: "평균이 아니라 홉 수별로")

**대조군에 같은 예산을 준다** — 그래프가 데려온 출처 문서 수만큼 BM25 에도 `k` 를
준다. 안 그러면 이긴 쪽이 예산 덕인지 구조 덕인지 갈리지 않는다.

~~**2·3홉에서 BM25 가 무너지는 것이 이 프로젝트의 증명이다.**~~
~~1홉은 답이 한 문서 안에 있어 BM25 도 잘한다 — 그것도 같이 보고한다.~~

#### 이 전제가 틀렸다 (7단계 실측, 2026-09-21)

```
            그래프    BM25
  1홉        100%     100%
  2홉         94%      94%
  3홉         57%      71%    ← BM25 가 더 낫다
  전체        88%      91%
  holdout     79%      93%    ← 14%p 뒤진다
```

**BM25 가 이겼다.** 증명하려던 것의 정반대가 나왔다.

**원인은 시스템이 아니라 내 골든셋이었다.** 기대 문서의 **69%가 질문에 이름이
나온 문서**였다 — BM25 는 그 이름만으로 그 문서를 찾는다. 경로가 그래프상 3홉이어도,
답의 근거가 질문 개체의 문서 안에 있으면 **그것은 멀티홉 문제가 아니다.**

| | 답이 있는 문서에 질문의 단어가 |
|---|---|
| 영화 | **없다** — 《기생충》 줄거리에 '송강호' 가 한 글자도 없다 → BM25 가 **원리적으로** 불가 |
| 한국사 | **있다** — 《안창호》 문서가 그가 세운 조직을 자기 안에 다 적는다 |

**위키백과 인물 문서는 그 인물의 관계를 자기 안에 다 적는다.** §1 에서 "한 문서만
읽어서는 답이 안 나온다" 고 한 전제가 영화만큼 강하게 성립하지 않았다.

#### 대응 — 채점표를 고치지 않고 묶음을 추가했다

기존 결과를 지우는 것은 채점표를 고치는 일이다. 대신 **BM25 가 원리적으로 못 푸는**
조건 — *답의 근거 문서에 질문 개체의 이름이 한 번도 안 나온다* — 으로 그래프를 훑어
41개 경로를 찾고, 그중 10문항을 `bridge-hard` 묶음으로 **추가**했다.

```
묶음           그래프    BM25
  tuned         95%      90%
  holdout       79%      93%    ← BM25 우세
  bridge-hard   90%      70%    ← 그래프 우세, 20%p
```

**같은 시스템인데 문항 성격에 따라 우열이 뒤집힌다.** 그래서 REPORT 에 쓸 결론은
"GraphRAG 가 BM25 보다 낫다" 가 아니라 이것이다 —

> **다리를 건너야만 닿는 질문에서만 낫고, 그런 질문은 위키백과 인물 도메인에서
> 생각보다 드물다.** 도메인이 도구를 고르지, 도구가 도메인을 이기지 않는다.

> **과제는 "basic RAG 대조" 라고 썼는데 여기서는 BM25 를 쓴다.** 대조군의 목적은
> "그래프 없이 키워드·유사도만으로 어디까지 되는가" 이고, BM25 는 **LLM·임베딩 호출이
> 0회**라 하루에 몇 번이고 공짜로 다시 잰다 (§6 와 같은 이유). 임베딩 대조군은 매번
> 비용이 들어 그 자리를 못 지킨다. **이 치환과 이유를 REPORT 3번에 적는다** —
> 요구를 안 읽은 것으로 보이지 않게.

시대별 표도 따로 낸다. **조선 쪽이 현대사보다 낮을 것으로 예상**하는데(위키백과 서술
밀도가 다르다), 예상이 맞는지 틀리는지를 숫자로 확인한다.

### 실패의 층 분류 (루브릭 명시)

틀린 문항마다 어디서 깨졌는지 **코드가 판정**한다.

| 층 | 판정 기준 | 고칠 자리 |
|---|---|---|
| **색인** | 기대 문서가 코퍼스에 **아예 없다** | 수집 |
| **탐색** | 코퍼스에 **있는데** 근거로 못 데려왔다 | 씨앗·홉·예산 |
| **생성** | 근거에 **있는데** 답변이 못 말했다 | 프롬프트·근거 표기 |

> **실측 — 색인 0건 · 탐색 4건.** 기대 문서가 코퍼스에 없어서 틀린 것은 하나도
> 없었다(수집이 제 몫을 했다). 4건 모두 `answer` 노드까지 갔는데 기대 문서가 근거에
> 없었다 — `trace` 가 `followup→route→seeds→expand→assemble→answer` 로 찍혀 있어
> **어디서 끊겼는지를 따로 추론할 필요가 없었다.**

> 영화에서 이 한 줄을 안 찍어 뒀다가, "손실이 아닌 칸" 안에 숨은 평가셋 오류를
> 눈으로 훑다 발견했다. 이번에는 처음부터 찍는다.

**코드 판정만으로는 루브릭을 못 채운다.** 루브릭은 *"실패 사례를 **직접 읽어** …
구분해 기록했는가"* 라고 쓴다. 그래서 자동 분류표 **옆에**, 대표 실패 3~5건을 손으로
읽고 이렇게 남긴다 — 질문 · 기대 경로 · **실제로 탄 경로**(`runs.jsonl` 에서) ·
원문 한 줄 · 어디서 왜 깨졌는지 · 고쳤는지(안 고쳤으면 그 이유).
**표는 분포를, 서술은 원인을 보여 준다.** 둘 다 REPORT 3번에 넣는다.

> **썼다 — [`docs/실패 정독.md`](실패%20정독.md)** (7.3단계, 대표 5건).
> 그중 하나는 **골든셋이 틀린 경우**였다 — "동학 농민 운동을 지휘한 인물" 을 김구로
> 상정했는데 모델이 전봉준으로 답했고 근거가 그것을 뒷받침한다. **모델이 맞고 내가
> 틀렸다.** 고치면 점수가 오르지만 시스템이 나아진 것이 아니므로 **고치지 않고
> 기록만 남긴다.**
>
> 또 하나는 **모델의 거절 판단을 믿을 수 없다**는 증거다. 거절 문항 8/8 을 막은 것은
> `route` 노드가 **LLM 전에 코드로** 걸렀기 때문이고, 모델 자신은 한쪽에서 있는 것을
> 없다 하고(6건) 다른 쪽에서 없는 경로를 지어냈다(`x-04`).

### 홀드아웃

스키마·별칭 사전·허브 기준을 **동결한 뒤** 새로 쓴 문항을 한 번만 채점한다.
튜닝 묶음과 나란히 보고한다 — **두 숫자의 격차가 과적합의 크기다.**
영화에서 그 격차가 18%p 였고, 97% 만 적었으면 그만큼 부풀려 말할 뻔했다.

> **실측 (7단계, 첫 채점) — `tuned 95%` · `holdout 79%` · 격차 16%p.**
> 영화의 18%p 와 거의 같다. 6단계 스윕이 **tuned 만 보고** 값을 골랐기에 이 숫자가
> 의미를 가진다 — holdout 을 보고 골랐으면 격차가 작게 나왔을 것이고, 그건
> 과적합이 없어서가 아니라 **재는 자를 오염시켰기 때문**이었을 것이다.

## 8. 화면 설계

```
app/
  layout.tsx          상단 도메인 탭 (🎬 영화 | 🏛 한국사) + 기존 3D 붙박이
  page.tsx            영화 질문          ← 경로 그대로. 첫 화면은 영화다
  browse/ map/        영화 탐색기·지도    ← 그대로
  history/
    page.tsx          한국사 질문
    browse/page.tsx   인물·조직·사건 탐색기 (시대 필터)
    map/page.tsx      관계 지도
  api/history/ask     질의
```

영화의 **화면 경로**(`/` · `/browse` · `/map`)는 건드리지 않는다. 바뀌는 것은
그 아래 질의 파이프라인이 공통 `StateGraph` 를 타게 되는 것뿐이고, **화면이 받는
결과의 모양은 같다** (§6 의 회귀 검증이 이것을 숫자로 지킨다).

아직 공개 전이라 링크가 깨질 걱정은 없지만, **돌아가는 코드를 이유 없이 만지면
이번 작업의 범위만 넓어진다.** 화면을 손대지 않는 이유가 그것이다.

한 화면에 반드시 같이 뜨는 것 (과제: "답변과 함께 탄 경로 · 근거 삼중항 · 출처 문서"):

```
답변    안창호는 신민회를 조직하였습니다.

경로    안창호 ─FOUNDED─▶ 신민회 ─RELATED_TO─▶ 105인 사건

삼중항  (안창호, FOUNDED, 신민회)
근거    "1907년 국내로 들어와 신민회를 조직하였다."
출처    위키백과 《안창호》
```

## 9. 제출물 매핑

과제가 보여 준 구조는 파이썬이다. 이 저장소는 TypeScript 이므로 **역할로 대응**시키고
그 대응표를 REPORT 에 싣는다.

| 과제 구조 | 이 저장소 |
|---|---|

**같은 구조가 두 번 있는 것**이고, REPORT 의 대응표에도 두 줄로 나란히 싣는다.

### REPORT.md 6개 항목 — **두 도메인을 함께 쓴다**

항목마다 두 도메인을 **나란히** 놓는다. 그러면 대조 자체가 논거가 된다 —
같은 설계를 **성질이 정반대인 두 코퍼스**에 적용한 결과이기 때문이다.

| # | 항목 | 🎬 영화 | 🏛 인물(한국사) |
|---|---|---|---|
| 1 | 주제와 코퍼스 | TMDB — **이미 구조화된** 크레딧 | 위키백과 **산문** 140건 · 600년으로 넓힌 대가 |
| 2 | 골든셋과 스키마 | `movie·person·collection` · 152문항 6묶음 | `Person·Organization·Event` · 관계 6종 · 40문항 · **뽑지 않은 관계와 그 대가** |
| 3 | 측정 결과 | 홉별 BM25 대조 · **홀드아웃 격차 18%p** | 홉별·시대별 BM25 대조 · 경로 재현율 · 실패 3층 |
| 4 | 파이프라인 구조도 | **그림 한 장을 공유한다** — 공통 LangGraph 노드·State 흐름(Mermaid) + 노드별 도메인 구현 대조표 (§6) | ← 같은 그림 |
| 5 | 데모 설계 | 탐색기 · 지도 · 3D 경로 | 질문 · 시대 필터 · 관계 지도 |
| 6 | 회고 | **갈라 쓰지 않는다** — 무엇이 도메인을 타고 무엇이 안 탔는지를 한 절에 | ← |

**이 대조가 REPORT 에서 가장 센 대목이다.** 구조화된 데이터(TMDB)에서는 규칙으로
관계가 나왔고 정제가 사실상 필요 없었다. 산문(위키백과)에서는 LLM 추출 · `quote`
원문 대조 · 별칭 병합이 **전부 필요했다.** 같은 파이프라인, 다른 대가 —
과제가 *"이전 GraphRAG 를 바탕으로 내 도메인에 적용"* 을 요구한 이유가 여기서 보인다.

> **쓰지 않을 표현** — "영화 코드를 재사용했다". 두 도메인은 **같은 앱의 두 축**이지
> 한쪽이 다른 쪽의 재탕이 아니다. 각 도메인에서 **실제로 만든 것**과 그때 든 대가를 적는다.

### 채점자가 실제로 돌릴 수 있어야 한다 (루브릭 1)

루브릭 1번은 *"문서 수집부터 답변 생성까지 전체 워크플로우가 **오류 없이 실행**되는가"*
다. `git clone` 한 사람이 무엇을 하면 되는지가 설계에 들어 있어야 한다.

| 무엇 | 왜 |
|---|---|
| **산출물을 저장소에 커밋** (`docs/` 140건 · `edges.raw.json` · `graph.json` · `eval.json`) | 채점자에게 위키 API 140건 + LLM 추출을 다시 돌리게 하면 안 된다. **clone 만으로 데모가 뜬다** |
| `package.json` 에 `history:fetch` · `history:extract` · `history:graph` · `history:eval` | 지금은 영화용 스크립트뿐이다. 재현하려는 사람은 단계별로 돌릴 수 있어야 한다 |
| `.env.example` | `OPENAI_API_KEY` 한 줄. 실제 키는 절대 커밋하지 않는다 |
| **키 없이 어디까지 되는지 README 에 명시** | 근거·경로·삼중항·출처·3D 는 **LLM 없이 전부 나온다.** 답변 문장 생성에만 키가 필요하다 |
| README 가 **두 도메인을 한 번에** 소개 | 지금 첫 줄은 "# 영화 네비게이터" 다. 제출물은 저장소 전체이므로 **"하나의 GraphRAG 엔진 · 두 도메인(🎬 영화 · 🏛 인물)"** 으로 다시 쓴다. 도메인마다 코퍼스 건수·스키마·평가 숫자를 **나란한 표**로 놓고, 실행법은 공통 + 도메인별로 나눈다 |
| **두 도메인 다 clone 만으로 떠야 한다** | 한쪽만 되면 "전체 워크플로우가 오류 없이 실행" 이 아니다. 영화 산출물(`data/graph.json` 등)도 커밋 상태를 확인한다 |

**7.5 를 뒤에 둔 이유** — 영화 전환은 **없어도 제출이 되는 일**이다. 인물 쪽 평가
숫자가 다 나온 뒤에 손대야, 막히면 그 자리에서 접고 §6 의 구조도만 인물로 내면 된다.
**기준선을 먼저 박는 것이 이 단계의 전부다.**

**1.5 를 단계로 둔 이유** — 밀도가 모자라면 그 뒤 전부가 헛일이 된다.
추출까지 다 하고 나서 "다리가 없다" 를 발견하면 되돌릴 것이 많다.

**6 을 7 앞에 둔 이유** — §6 은 홉 상한과 허브 기준을 "재고 나서 정한다" 고 선언했다.
그 측정이 어디서 나오는지를 단계로 두지 않으면, 결국 잠정값을 그대로 쓰고
사후에 이유를 붙이게 된다. **과제가 요구한 것은 기준이 아니라 기준의 근거다.**

| 동명이인 오병합 | 중 | 구분 못 하면 합치지 않고 리포트에 찍는다 |
| 추출 비용 | 작 | 문서 140건 × 1회. 빌드 시점 한 번뿐 |
| **영화를 공통 그래프에 얹다가 망가뜨림** | **큼** (전환을 택했으므로 올라갔다) | 로직은 옮기지 않고 **노드가 기존 순수 함수를 호출만** 한다. 전환 **전에** 152문항 기준선을 박고, 전환 **후** 같은 문항으로 재검증해 **한 칸이라도 움직이면 되돌린다**. 화면 경로는 손대지 않는다. 7.5 단계라 **접어도 제출에 구멍이 안 난다** |
| **범위가 과제 최소를 크게 넘는다** | 중 | 과제 최소는 평가셋 10문항인데 설계는 40문항 + 3층 + 시대별 + 홀드아웃 + 스윕 + 영화 전환이다. **필수(10문항 · 홉별 · 층별 · 데모 · REPORT 6항목)를 먼저 끝내고** 시대 교차·홀드아웃·hop-sweep·영화 전환·**외부 인물 API 검증(§5)** 은 시간이 남을 때 붙인다. **순서를 뒤집지 않는다** |
| LangGraph 도입이 시간을 먹는다 | 작 | 탐색·씨앗·조립이 전부 순수 함수라 노드가 감싸기만 하면 된다. 새로 쓰는 것은 `zod` State 스키마뿐. **하루 안에 안 되면 (b) 직접 State 머신으로 내린다** — 다이어그램과 `runs.jsonl` 은 어느 쪽이든 나온다 |
